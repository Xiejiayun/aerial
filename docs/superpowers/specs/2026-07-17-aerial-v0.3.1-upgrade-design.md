# Aerial v0.3.1 Compatibility and Release Design

Date: 2026-07-17
Status: approved for specification; implementation requires written-spec review

## Context

Aerial 0.2.7 is the current `main` version. The local checkout and
`origin/main` both point at `5be62a4`. The baseline passes 341 tests, syntax
checks, the package allowlist, the secret scan, and `npm audit` with no known
vulnerabilities.

The live Copilot model catalog still advertises the routes Aerial relies on:
`responses`, `responses_websocket`, `messages`, and `chat`. From the current
Shanghai direct route, the catalog has nine Responses models but no Messages
models. This confirms that Claude Code compatibility remains region-dependent
and that Aerial must continue treating the live catalog as authoritative.

Current Codex 0.142.0 loads Aerial's custom provider successfully. Its
`responses` wire API, `/v1` base URL, and command-backed authentication are
healthy. Aerial must not set Codex `supports_websockets = true`: Aerial accepts
client traffic over HTTP and only uses Copilot's `ws:/responses` route as an
optional internal upstream transport.

Claude Code's current interface supports `low`, `medium`, `high`, `xhigh`, and
`max`. Claude Code 2.1.203 and later also document `ultracode`. Aerial 0.2.7
currently collapses `max` to `xhigh` before it can inspect model capabilities
and does not recognize `ultracode`.

GitHub does not document the Copilot subscription endpoints used by Aerial as a
stable third-party inference API. Consequently, fixed model lists or inferred
endpoint contracts are out of scope; compatibility must be based on observed
catalog metadata with conservative fallbacks.

The `v0.2.7` GitHub Actions release completed successfully and its registry
smoke installed 0.2.7 from the matching commit. The version was subsequently
removed from npm, whose current `latest` is 0.2.6. Version 0.2.7 must not be
reused. The requested next public version is 0.3.1.

## Goals

- Preserve Claude `max` when the selected Copilot model advertises it.
- Accept Claude `ultracode` input and safely resolve it to a catalog-supported
  effort without requiring every installed Claude Code version to understand
  that value in persisted settings.
- Keep existing Claude behavior unchanged for `low` through `xhigh`.
- Keep Codex and Copilot routing behavior unchanged unless current evidence
  demonstrates a compatibility problem.
- Make release preflight reject version reuse, non-monotonic versions,
  tag/version mismatches, dirty tracked files, and ambiguous registry errors.
- Publish and verify npm package 0.3.1 and a matching GitHub Release.
- Capture the complete upgrade and release workflow in a reusable project Skill.

## Non-goals

- Publicly expose a WebSocket endpoint from Aerial.
- Replace catalog-driven model selection with a hard-coded model list.
- Add unsupported Copilot endpoints such as embeddings.
- Change Copilot client-identification headers that still pass live probes.
- Re-publish or restore npm version 0.2.7.
- Delete or commit the unrelated `.codex-unpublish-old.cjs` worktree file.

## Approach

### 1. Claude effort compatibility

Separate Claude's accepted input vocabulary from the effort written on the
wire. The accepted order becomes `low`, `medium`, `high`, `xhigh`, `max`, and
`ultracode`. Resolution follows the same model-aware rule already used for
Codex:

1. Preserve an exact effort when the live selected model advertises it.
2. Otherwise select the highest advertised effort below the request.
3. If only higher efforts exist, select the model's lowest advertised effort.
4. Without catalog metadata, preserve the existing safe ceiling by mapping
   `max` and `ultracode` to `xhigh`.

`ultracode` is accepted as user intent, but setup persists `max` or the nearest
lower model-supported effort, never the literal alias. This keeps settings
usable with Claude Code releases older than 2.1.203. Request routing still
recognizes a literal `ultracode` sent by a newer client and may preserve it on
the wire when the live Copilot catalog explicitly advertises it.

Apply the resolver in both setup and `/v1/messages` request routing. Continue
supporting `thinking.type = "enabled"` migration to adaptive thinking and do
not override explicit `output_config.effort` values before resolution.

### 2. Provider stability

Retain the current Codex provider shape and HTTP client transport. Continue to
forward the client's `anthropic-version` and `anthropic-beta` headers and use
the existing default Anthropic API version only when the client omits it.

Treat Copilot model catalog fields as optional. Catalog refresh failure must
not make an otherwise valid request fail; the conservative effort fallback
applies instead. No header or route is changed merely because a newer client
package exists.

### 3. Release reliability

Add a deterministic release-preflight script with `new-release` and `workflow`
modes. Use the former locally before creating a tag and the latter in the
release workflow. It must:

- require an exact clean stable version and the repository's `0.A.B` policy,
  where `B` is 1 through 9;
- require target 0.3.1 for this release;
- verify `package.json` and `package-lock.json` agree;
- require the target version to be greater than all published stable versions;
- distinguish registry E404 from network, authentication, and server errors;
- in `new-release` mode, fail if the target npm version already exists, even
  when its `gitHead` matches;
- in `workflow` mode, allow an existing target only when its `gitHead` matches
  the checked-out release commit so post-publish recovery remains idempotent;
- verify `main`, `origin/main`, the release tag, and the release commit agree at
  the appropriate stage.

Keep the workflow's idempotent already-published path for rerunning the same
release after publishing. The stricter local preflight protects creation of a
new release; workflow idempotency protects recovery after publication.

The release sequence is:

1. Merge or push every approved compatibility and release change to `main` as
   a separate tested commit.
2. Bump both npm manifests and user-facing release notes to 0.3.1 in a dedicated
   commit and push it.
3. Run the full local release gate.
4. Create and push annotated tag `v0.3.1`.
5. Watch the Release workflow through publish and exact-version smoke.
6. Verify npm `0.3.1`, `latest`, registry `gitHead`, provenance, CLI version,
   CLI help, tag commit, and GitHub Release.

### 4. Reusable Skill

After 0.3.1 is published, initialize `skill/aerial-release/` with the Skill
Creator tooling. The Skill will contain:

- a concise `SKILL.md` describing discovery, official-source API review,
  compatibility decisions, version policy, atomic commits, release, recovery,
  and final verification;
- `agents/openai.yaml` generated from the completed Skill;
- a deterministic read-only preflight helper only if it adds checks not already
  provided by the repository's release script.

Validate the Skill with `quick_validate.py`, exercise its read-only preflight,
then commit and push it to `main` after the release tag. The Skill is repository
source material and is not required to be part of the npm package allowlist.

## Error handling

- A missing or stale Copilot catalog uses conservative effort fallbacks and
  emits a structured routing reason.
- Unsupported explicit Claude effort values fail before any setup file or
  Aerial key is written.
- Registry errors other than a confirmed E404 stop the release.
- A published target with a different or missing `gitHead` stops the release.
- A failed workflow is diagnosed and rerun only after the same commit remains
  on `main`; never move or overwrite a published tag.
- A failed post-publish smoke is recovered through workflow idempotency, not by
  bumping or republishing blindly.

## Verification

Add focused tests for:

- Claude effort normalization and ordering;
- exact `max` preservation from catalog metadata;
- `max` and `ultracode` downgrade behavior;
- setup selection, persisted settings, status reporting, and help text;
- Messages request routing with singular and plural catalog effort fields;
- catalog-unavailable fallback behavior;
- release-preflight version policy, registry tri-state, manifest mismatch,
  monotonicity, and git/tag checks.

Before each push, run the focused tests for that change. Before tagging, run
syntax checks, all tests, secret scanning, package verification, audit, npm pack
inspection, and CLI help/version smokes. After publication, install exactly
`@jiayunxie/aerial@0.3.1` in a clean temporary directory and verify its output.
